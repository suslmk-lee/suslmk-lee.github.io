01Buzz란 무엇인가

Buzz는 사람과 AI 에이전트가 같은 방을 쓰는 자체 호스팅 워크스페이스다. Block, Inc.가 만들었고 Apache 2.0으로 공개돼 있다.

지금 대부분의 팀은 채팅 도구와 코드 호스팅, 봇, CI 대시보드, 릴리스 도구, 검색 색인을 따로 두고 그 사이를 접착 코드로 잇는다. 탭 일곱 개가 서로의 존재를 아는 척하는 상태에서, 어떤 결정이 왜 내려졌는지는 어느 도구에도 온전히 남지 않는다. Buzz는 이 조각들을 하나의 기반 위로 옮긴다.

하나의 로그, 하나의 신원 모델

기반은 Nostr 릴레이다. 메시지든 이모지 반응이든 워크플로 단계든 리뷰 승인이든 git 이벤트든, 전부 하나의 로그에 서명된 이벤트로 쌓인다. 작성자가 사람이든 프로세스든 형태와 신원 모델, 감사 추적이 동일하다는 점이 핵심이다.

그래서 이런 것들이 부수적으로 따라온다.

  • 대화 · 패치 · CI 실행 · 승인을 한 번에 검색 — 전부 같은 종류의 이벤트이므로
  • 누가 무엇을 했는지 해시 체인 감사 로그
  • “이 코드가 왜 존재하는가”의 근거가 채널 자체에 남음
블록체인이 아니다

서명된 이벤트를 쓰지만 체인도 토큰도 없다. 프로젝트 문서가 직접 못 박아 둔 문장이다 — “서명된 이벤트는 기념 코인을 사지 않아도 유용하다.”

커뮤니티 = URL

사용자가 URL로 접근하는 작업 공간을 커뮤니티라 부른다. 지금 배포되는 단일 릴레이 구성에서는 릴레이 URL 하나가 커뮤니티 하나를 가리킨다. 호스팅 사업자가 여러 도메인 뒤에 여러 커뮤니티를 둘 수도 있지만, URL이 작업 공간을 결정한다는 규칙은 그대로다.

이 규칙은 개념적 선언이 아니라 코드에 박혀 있다. 릴레이는 요청의 Host 헤더로 커뮤니티를 고르고, 매핑되지 않은 Host는 fail-closed로 거절한다. 이 문서의 §8.1과 §9.4가 그 결과다.

지금 되는 것 / 아직인 것

프로젝트가 스스로 공개한 표를 요약하면 이렇다. 완성된 제품이 아니라는 점을 문서에 그대로 적어 두었다.

02구성 요소

릴레이 하나를 단일 진실 공급원으로 두고, 그 위아래에 클라이언트와 저장소를 붙이는 구조다. 사람이 쓰는 데스크톱 앱, 에이전트, 명령줄 도구가 모두 같은 프로토콜로 릴레이에 접속한다.

릴레이는 NIP-01과 NIP-42 인증을 처리하고 채널·DM·미디어·워크플로·git에 대한 REST 경로와 감사 로그를 담당한다. 그 뒤로 Postgres(이벤트 + 전문검색), Redis(pub/sub·접속 상태), S3 호환 저장소(첨부 파일)가 붙는다. 구현은 목적별로 잘게 나눈 Rust 크레이트 묶음이다.

ACP — 에이전트를 갈아끼우는 규격

LSP가 “에디터 M개 × 언어 N개”를 M+N으로 바꿨듯, ACP(Agent Client Protocol)는 “UI M개 × 코딩 에이전트 N개”를 같은 방식으로 푼다. stdio 위 JSON-RPC 2.0이며, 클라이언트가 에이전트를 자식 프로세스로 띄운다.

MCP와 헷갈리기 쉬운데 방향이 반대다. 둘은 경쟁이 아니라 위아래로 붙는 층이다.

사람 / UI  (Buzz Desktop)
     │  ACP        ← 위에서 에이전트를 부른다
     ▼
에이전트  (Claude Code, Goose, buzz-agent, samanda-acp)
     │  MCP        ← 아래로 도구를 부른다
     ▼
도구  (파일시스템, 셸, DB, buzz CLI)

ACP는 양방향이다. 에이전트가 파일을 고치려 할 때 session/request_permission으로 사람에게 되묻는다. 단방향 RPC로는 못 하는 일이고, 사람이 루프 안에 남는 근거다.

덕분에 Buzz는 Devin · Cursor · OpenCode · Kimi · Grok · Amp를 프리셋으로 나열하고, ACP를 말하는 실행 파일이면 무엇이든 커스텀 하네스로 등록할 수 있다. §7.2의 Samanda 셔틀이 정확히 그 방식이다.

03에이전트는 멤버다

Buzz의 핵심 주장 하나 — 에이전트를 봇이 아니라 팀원으로 만든다.

보통 채팅 봇은 특별 취급이다. 별도 권한 시스템, 별도 API, @bot help. Buzz는 그걸 없앴다. 에이전트도 사람처럼 자기 키페어를 갖고, 채널에 초대되고, 자기 감사 로그를 남긴다. 권한 플래그가 아니라 신원으로 범위가 정해진다 — 신입 동료에게 접근 권한을 주는 방식 그대로다.

에이전트가 들어와서 실제로 할 수 있는 일도 사람 동료와 같은 범위다. 저장소를 열고, 패치를 보내고, 코드를 리뷰하고, 워크플로를 돌리고, 캔버스를 편집하고, 다른 에이전트를 지휘하고, 채널을 만들고, 봐야 할 사람을 불러온다. 다른 점은 권한 플래그가 아니라 키가 다르다는 것뿐이다.

프로젝트가 드는 세 가지 장면

  1. 장애 기억 — 새벽 2시에 “이 오류를 전에 본 적 있나”라고 물으면, 채널을 지켜보던 에이전트가 6개월치 기록에서 관련 스레드와 근본 원인, 수정 내역을 찾아 붙이고 마지막으로 배포한 사람을 호출할지 물어본다.
  2. 브랜치가 곧 방 — 기능 브랜치를 열면 채널이 하나 생긴다. 패치는 NIP-34 이벤트로 들어오고, CI가 결과를 남기고, 에이전트가 1차 리뷰를 돌린 뒤, 병합 결정이 근거와 같은 방에 남는다.
  3. 스스로 쓰이는 릴리스 — 태그를 달면 워크플로가 시작되어 에이전트가 병합된 PR을 읽고 릴리스 노트 초안을 올린다. 사람이 반응 이모지로 승인하면 배포가 진행된다.

에이전트가 채널에 말하는 방법

알아둘 실무 사실 하나. 에이전트의 출력은 도구 호출이다. 생성한 텍스트는 클라이언트에 진행 상황으로 흘러갈 뿐, 채널에 글이 올라가는 유일한 경로는 에이전트가 buzz messages send를 실제로 실행하는 것이다.

이 사실이 §7.2에서 왜 셔틀이 필요한지를 결정한다. 도구 호출을 내지 않는 에이전트를 Buzz에 붙이면, 답은 로그에만 남고 채널은 조용하다.

깨어나는 조건

기본값은 멘션 전용이다. 이벤트의 p 태그에 자기 pubkey가 있어야 반응한다. 이름을 텍스트로 쓰는 게 아니라 서명된 이벤트의 태그라서, 정확한 표시 이름으로 멘션해야 한다.

환경변수효과
BUZZ_ACP_NO_MENTION_FILTER=1멘션 없이도 채널 메시지에 반응
BUZZ_ACP_SUBSCRIBE=all채널의 모든 이벤트 전달
BUZZ_ACP_RESPOND_TO작성자 게이트 — owner-only(기본) / allowlist / anyone / nobody
무한 루프 주의

작성자 게이트는 owner ∪ allowlist ∪ 형제 에이전트다. 같은 채널의 두 에이전트에게 동시에 멘션 필터를 끄면 서로에게 반응하며 무한 핑퐁이 된다. 토큰은 실제로 소모된다.

6.2S3 버킷

Ceph 노드에서 Buzz 전용 RGW 계정을 만든다. 릴레이는 버킷을 자동 생성하지 않으므로 버킷도 함께 만들어야 한다.

radosgw-admin user create --uid=buzz --display-name="Buzz Relay"

# 클러스터 안에서 mc Job 으로 생성
mc alias set rgw http://ceph-rgw.storage.svc.cluster.local:8080 "$AK" "$SK" --api S3v4
mc mb --ignore-existing rgw/buzz-media

6.3시크릿

차트는 secrets.existingSecret을 쓰면 Secret을 하나도 만들지 않는다. 번들 Redis가 참조하는 buzz-relay까지 직접 만들어야 한다 (§9.3).

REDISPASS=$(openssl rand -hex 24)
PGPASS=$(kubectl get secret buzz.buzz-db.credentials.postgresql.acid.zalan.do \
           -n buzz -o jsonpath='{.data.password}' | base64 -d)

kubectl -n buzz create secret generic buzz-relay \
  --from-literal=redis-password="$REDISPASS"

kubectl -n buzz create secret generic buzz-secrets \
  --from-literal=BUZZ_RELAY_PRIVATE_KEY=$(openssl rand -hex 32) \
  --from-literal=BUZZ_GIT_HOOK_HMAC_SECRET=$(openssl rand -hex 32) \
  --from-literal=DATABASE_URL="postgres://buzz:${PGPASS}@buzz-db.buzz.svc.cluster.local:5432/buzz" \
  --from-literal=REDIS_URL="redis://:${REDISPASS}@buzz-redis.buzz.svc.cluster.local:6379" \
  --from-literal=BUZZ_S3_ACCESS_KEY='<RGW access key>' \
  --from-literal=BUZZ_S3_SECRET_KEY='<RGW secret key>'
복구 불가

BUZZ_RELAY_PRIVATE_KEY는 릴레이 신원 그 자체다. 잃으면 복구할 수 없고, 바꾸면 다른 릴레이가 된다. 생성 즉시 백업할 것.

6.5에이전트

각 에이전트는 자기 키페어를 갖고 릴레이 멤버로 등록돼야 한다. 키페어를 공유하면 안 된다.

kubectl exec -n buzz deploy/buzz -- buzz-admin generate-key
kubectl exec -n buzz deploy/buzz -- buzz-admin add-member --pubkey <pubkey>

kubectl apply -f agent-scout.yaml      # OpenAI
kubectl apply -f agent-samanda.yaml    # 사내 agent API

# 채널 참여 + 프로필 — 에이전트가 스스로 수행한다
kubectl exec -n buzz deploy/buzz-agent-scout -- buzz channels join --channel <UUID>
kubectl exec -n buzz deploy/buzz-agent-scout -- buzz users set-profile --name "Scout"

07에이전트 통합 3가지

세 종류를 붙였고 구조가 각각 다르다. 하나는 Buzz 네이티브, 둘은 외부 에이전트를 잇는 셔틀이다. 셔틀이 필요했던 이유는 서로 달랐다.

7.1Scout — Buzz 네이티브

buzz-agent가 도구 루프를 직접 돌린다. buzz CLI로 메시지 발행, 이슈 생성, PR 열기까지 가능하다. 커스텀 이미지가 필요 없다 — buzz-agent가 sprig 이미지에 이미 들어 있다.

7.2Samanda — ACP 셔틀

Samanda(agent-api)는 모델이 아니라 에이전트다. /v1/chat/completions가 자체 agent loop를 돌려 완성된 산문을 반환하며 tool_calls를 내지 않는다. §3에서 본 대로 Buzz는 도구 호출로만 메시지를 발행하므로, 셔틀이 그 한 걸음을 대신한다.

buzz-acp ──ACP/stdio──▶ samanda-acp ──HTTP──▶ agent-api /v1
                             │
                             └─▶ buzz messages send   (subprocess)

이미지 빌드가 없다. sprig는 musl 정적 바이너리(13MB)라 아무 Alpine 위에서나 돈다.

  • initContainer (buzz-sprig) → sprig + 심볼릭 링크 6개를 emptyDir로 복사
  • main (python:3.13-alpine) → Python 런타임 제공
  • ConfigMap/samanda-acp → 셔틀 스크립트를 0755로 마운트

덕분에 Harbor 자격증명도 로컬 Docker도 필요 없고, 셔틀 수정이 CI 왕복 없이 끝난다.

kubectl -n buzz create configmap samanda-acp \
  --from-file=samanda-acp=./samanda-acp \
  --dry-run=client -o yaml | kubectl apply -f -
kubectl -n buzz rollout restart deploy/buzz-agent-samanda
환경변수값이유
SAMANDA_BASE_URLhttp://agent-api.internal.svc.cluster.local:8000/v1내부 직결 — TLS 문제 원천 제거
SAMANDA_READ_TIMEOUT600기본 120초로는 도구 실행이 긴 턴에서 끊김
BUZZ_ACP_MULTIPLE_EVENT_HANDLINGqueue셔틀은 턴 중간 취소 불가 (§9.6)

7.3Hermes — ACP를 말하는데도 셔틀이 필요했다

Nous Research의 Hermes Agent를 역할별로 5개 붙였다. hermes acp 서브커맨드가 있어 처음엔 셔틀 없이 바로 연결했다. ACP 핸드셰이크도 통과했다.

그런데 답을 하지 않았다. 멘션을 받고 반응 이모지까지 남긴 뒤, 도구를 20회 넘게 돌리며 환경을 탐색하다 아무것도 발행하지 않고 턴을 끝냈다.

시도결과
SOUL 프로필에 "반드시 발행하라" 규칙 추가변화 없음
<base> 프롬프트 제거 (22k → 13.5k 토큰)변화 없음
모델 교체 (사내 vLLM → OpenAI)동일 — 모델 문제가 아님
platform_toolsets로 도구 제한ACP 경로에 적용되지 않음

두 모델이 같은 행동을 보인 것이 결정적이었다. 모델이 아니라 모드의 문제였다.

모드성격-t 도구 제한
hermes acp자율 세션 — 에디터가 옆에 있다고 가정하고 스스로 작업불가
hermes -z한 번 묻고 한 번 답함가능

ACP의 일반 계약은 클라이언트가 에이전트의 agent_message_chunk를 렌더링하는 것이다. Zed나 VS Code가 그렇게 동작한다. 그런데 Buzz는 그 청크를 로그로만 남기고, 채널 발행은 오직 도구 호출로만 일어난다. Claude Code나 Goose가 잘 붙는 것은 하네스가 MCP로 CLI를 쥐여주고 기본 프롬프트로 훈련시키기 때문이다. Hermes는 자기 판단으로 움직였다.

그래서 Samanda와 같은 셔틀을 하나 더 만들었다. hermes -z를 호출하고 발행까지 맡는다.

buzz-acp ──ACP/stdio──▶ hermes-acp ──subprocess──▶ hermes -t <toolsets> -z "..."
                            │
                            └─▶ buzz messages send
자율 모드셔틀 경유

소요7분 초과12.8초

도구는 역할에 맞게 다르게 준다. 조율만 하는 역할은 도구가 없는 편이 빠르고, 조사가 필요한 역할에만 셸과 파일 접근을 준다.

모델 — 사내 vLLM에서 내려왔다

처음엔 사내 LiteLLM의 SAMANDA-V3(vLLM qwen-qwen3-8-27b-fp8)를 썼다. 2026-09-03 07:03 UTC에 그 Deployment가 0/0으로 내려갔고, 이 클러스터에는 GPU 노드가 없어 다시 뜨지 못한다. 사내 서빙 7개가 모두 같은 상태다.

Ready=True를 믿지 말 것

InferenceService는 계속 Ready: True라고 보고한다. 진실은 predictor Service의 Endpoints에 있다 — 거기가 <none>이면 죽은 것이다.

kubectl get endpoints <name>-predictor -n ai-kosmosai
# ENDPOINTS = <none>  ← Ready=True 여도 죽어 있다

더 나쁜 건 그다음이다. 백엔드가 죽은 뒤에도 SAMANDA-V3를 부르면 오류가 아니라 200이 온다. LiteLLM이 조용히 OpenRouter의 z-ai/glm-5.1로 넘기기 때문이다. 응답 본문의 모델 이름을 보기 전까지는 알 수 없고, LiteLLM의 /v1/model/info는 그 모델을 여전히 location: internal이라고 보고한다.

{"id":"gen-1788496137-...","model":"z-ai/glm-5.1", ...}
#      ^^^ OpenRouter 형식 id       ^^^ 사내 모델이 아니다

사내 모델을 부르는 줄 알면서 외부 제공자로 나가는 상태는 단순 장애보다 나쁘다. 그래서 claude-sonnet-5로 명시 전환했다 — 어차피 외부로 나갈 것이라면 설정에 그렇게 적혀 있어야 한다. GPU가 돌아오면 hermes-config.yaml의 model.default 한 줄만 되돌리면 된다.

이중 발행 주의

발행 주체가 셔틀로 바뀌면 프로필의 "직접 buzz messages send로 발행하라" 지시를 반드시 함께 걷어내야 한다. 셸 도구를 가진 역할이 그 지시를 따르면 같은 답이 두 번 올라간다.

08반드시 지킬 규칙

8.1릴레이 URL은 문자열이 정확히 일치해야 한다

에이전트의 BUZZ_RELAY_URL은 릴레이의 RELAY_URL과 완전히 같아야 한다. 두 군데에서 검증하며, 둘 다 관대하지 않다.

  1. Host → 커뮤니티 — communities.host (UNIQUE(lower(host))) 조회. buzz_core::tenant::normalize_host()는 :443과 :80만 제거한다. 서비스 DNS(:3000)로 붙으면 404.
  2. NIP-42 relay 태그 — buzz_auth::nip42::normalize_relay_url()은 스킴을 정규화하지 않는다. ws://로 붙으면 RelayUrlMismatch → nip42_invalid.

그래서 클러스터 안의 에이전트도 공개 URL 그대로 wss://buzz.example.com로 붙고, hostAliases로 인그레스 IP를 가리킨다.

8.2키페어 하나 = 인스턴스 하나

replicas: 1
strategy: { type: Recreate }   # RollingUpdate 면 같은 nsec 으로 2개가 동시에 붙는다

프로바이더 프로토콜을 우회해 직접 배포하므로, 이 유일성(remote-agents.md의 I4 불변식)은 운영자 책임이다.

8.3프로세스는 풀에 상주한다

buzz-acp는 에이전트 프로세스를 턴마다 새로 띄우지 않는다(AgentPool). 환경변수나 셔틀 코드를 바꿨으면 반드시 재시작해야 한다.

kubectl -n buzz rollout restart deploy/buzz-agent-<name>

“고쳤는데 왜 그대로지”의 대부분이 이것이다.

09트러블슈팅

실제로 물린 것만 담았다. 전부 소스나 로그에서 원인을 확인한 항목이다.

9.1buzz-db가 Creating에서 멈춤

could not generate Spilo env vars: could not read Secret PodEnvironmentSecretName:
still failing after 200 retries: secrets "spilo-wal-backup-env" not found

Zalando 오퍼레이터가 pod_environment_secret을 전역(watched_namespace: *)으로 요구한다. postgresql CR이 있는 네임스페이스마다 그 시크릿이 있어야 한다 → §6.1. 같은 이유로 postgres-system의 다른 postgresql CR가 SyncFailed 상태이며, 동일하게 복사하면 해소된다.

9.2릴레이 CrashLoop — relation "events" does not exist

차트 기본 이미지 appVersion 0.1.0이 죽은 태그다. 마이그레이션을 실행하지 않는다. ghcr.io/block/buzz에 시맨틱 태그는 0.1.0뿐이고 실제 릴리스는 latest(v0.2.1)로 나간다.

image:
  digest: sha256:4e31b7c7abb7d00b6f513dc559e58d2b980416f1dc400aa01bcf762cf2989cfc

9.3Redis 파드가 시작하지 못함

secrets.existingSecret을 쓰면 차트가 Secret을 0개 렌더링한다. 번들 Redis는 secretKeyRef: {name: buzz-relay, key: redis-password}를 optional 없이 참조한다 → §6.3에서 직접 생성.

9.4외부에서 404 — DNS

*.example.com 와일드카드가 203.0.113.99로 잡혀 있고 실제 서비스는 203.0.113.10이다. 개별 A 레코드가 필요하다.

buzz.example.com   A   203.0.113.10

레코드 추가 전에는 클라이언트마다 hosts 우회. 와일드카드 인증서라 TLS는 그대로 검증되고, 데스크톱은 reqwest / tokio-tungstenite를 시스템 리졸버로 쓰므로 hosts가 적용된다.

echo "203.0.113.10 buzz.example.com" | sudo tee -a /etc/hosts
# Buzz Desktop 완전 종료 후 재시작 — 앱이 DNS 를 캐시한다

증상원인

steer: no active_run_id and agent did not advertise _session/steering

기본값 meh=Steer는 진행 중인 턴에 새 메시지를 끼워넣으려 하고, 실패하면 session/cancel 후 5초 안에 응답을 기다린다. 셔틀은 블로킹 HTTP 한 방이라 중단이 안 되어 프로세스가 강제 종료된다 → BUZZ_ACP_MULTIPLE_EVENT_HANDLING=queue.

9.7OpenAI model_not_found

Project `proj_...` does not have access to model `gpt-5`

키의 프로젝트 권한을 먼저 확인할 것. 조직 계정이라도 프로젝트마다 접근 가능한 모델이 다르다.

curl -s https://api.openai.com/v1/models -H "Authorization: Bearer $KEY" \
  | python3 -c "import sys,json;print(sorted(m['id'] for m in json.load(sys.stdin)['data']))"

kubectl exec -n buzz buzz-db-0 -c postgres -- \
  curl -s http://buzz.buzz.svc.cluster.local:9102/metrics | grep buzz_auth_failures_total

# Host 라우팅 확인
kubectl exec -n buzz buzz-db-0 -c postgres -- \
  curl -s -o /dev/null -w "%{http_code}\n" -H "Host: buzz.example.com" \

# 셔틀의 SSE 스트림 요약
kubectl logs -n buzz -l app=buzz-agent-samanda -c harness | grep "stream done"

terminator=[DONE]이면 정상 종료, terminator=EOF면 연결이 중간에 끊긴 것(프록시 idle timeout 계열)이다.

9.9범용 에이전트가 답을 만들고도 발행하지 않음

Buzz는 도구 호출로만 채널에 글이 올라간다. 코딩 에이전트처럼 도구가 많은 상대는 프롬프트를 조사할 과제로 받아들여, 답을 만들고도 발행 단계에 도달하지 못한다. 로그에는 도구 성공만 남고 오류가 없어 원인이 잘 보이지 않는다.

배관을 의심하기 전에 도구가 성공하는데 발행만 없는지 확인하면 빠르다. 그렇다면 막힌 게 아니라 부르지 않는 것이다. §7.3의 셔틀 패턴으로 우회한다.

9.10에이전트가 도구 실행 시 환경변수를 걸러냄

{"error":"auth_error","message":"auth error: BUZZ_PRIVATE_KEY is required"}

시크릿 유출을 막기 위해 명령 실행 환경을 새로 구성하는 에이전트가 있다. 컨테이너 env에 키를 넣어도 도구가 실행하는 명령에는 전달되지 않는다. 로그인 셸의 PATH 재설정도 같은 계열의 증상이다.

키를 파일에 두고 얇은 래퍼가 주입하는 것으로 푼다. argv에 넣으면 ps에 노출되므로 env로 넘긴다.

#!/bin/sh
BUZZ_PRIVATE_KEY="$(cat /opt/buzz/.key)" exec /opt/buzz/bin/buzz "$@"

10.2업그레이드 — GitOps

배포는 ArgoCD app-of-apps로 옮겨졌다. 매니페스트는 AI-InfraOps/buzz, Application은 CICD/gitops에 산다. 마이그레이션은 릴레이 바이너리에 내장돼 있고 BUZZ_AUTO_MIGRATE=true로 기동 시 실행되며, 다중 복제본은 Postgres advisory lock으로 안전하다.

이미지 태그는 전부 다이제스트로 고정한다. 업스트림에 시맨틱 태그가 없어(latest / main / sha-*) 움직이는 태그를 직접 참조하면 어제와 오늘의 배포가 달라진다.

에이전트 — 자동

argocd-image-updater가 2분마다 업스트림을 보고, 새 이미지가 있으면 k8s/kustomization.yaml의 images를 저장소 main에 직접 커밋한다. ArgoCD가 그 커밋을 받아 롤아웃한다. 흔히 쓰는 .argocd-source-*.yaml 오버라이드 방식은 저장소와 실물을 어긋나게 하므로 쓰지 않았다.

이미지쓰는 곳전략
ghcr.io/block/buzz-sprig:main에이전트 7개 전부의 initContainerdigest — 움직이는 태그의 다이제스트를 추적
nousresearch/hermes-agentHermes 5개semver — vYYYY.M.D 중 최신
v1.x는 CRD 방식이다

argocd-image-updater v1.1.1은 Application 어노테이션을 읽지 않는다. 로그의 controllerKind=ImageUpdater가 그 신호다. 설정은 ImageUpdater 커스텀 리소스로 쓴다. 어노테이션만 붙여 두면 오류도 없이 아무 일도 일어나지 않는다.

digest 전략은 어느 태그를 추적할지 이미지 이름에 적어야 한다. 빠뜨리면 매 주기 cannot use update strategy 'digest' ... without a version constraint로 실패한다.

kubectl -n argocd logs deploy/argocd-image-updater-controller | grep "Processing results"
# images_considered=2 images_skipped=0 images_updated=2 errors=0

릴레이 — 수동, 알림만 자동

릴레이는 자동 갱신 대상에서 뺐다. BUZZ_AUTO_MIGRATE=true이므로 이미지 교체가 곧 비가역 DB 마이그레이션이다. 컨트롤러가 새벽에 조용히 스키마를 바꾸게 둘 수는 없다.

대신 relay-update-notify CronJob이 매일 09:00 KST에 살아있는 Deployment/buzz의 다이제스트와 업스트림 latest를 비교하고, 다르면 팀 채널에 메시지를 보낸다. 적용은 사람이 values-prod.yaml을 고쳐 커밋한다.

비교 대상을 매니페스트에 상수로 베껴 두지 않고 클러스터에서 직접 읽는 것이 요점이다. 베껴 두면 릴레이를 올릴 때 그 값도 같이 고쳐야 하고, 잊는 순간 매일 거짓 알림이 온다 — 자동화 안에 수동 단계를 남기는 셈이다. 릴레이가 다이제스트 없이 태그로만 고정돼 있으면 값이 비고 잡이 실패한다. 조용히 틀린 비교를 하는 것보다 낫다.

10.3HA로 확장할 때

  • Redis 하드 요구 — 없으면 차트가 렌더링 단계에서 실패한다
  • persistence.git.enabled: false로 변경 — RWO PVC는 노드 하나에 묶여 멀티팟 스케줄링을 막는다. git 상태는 S3 + Postgres가 원본이라 emptyDir로 충분하다
  • 허들 오디오는 SFU 부재로 자동 비활성화된다
용량 확인

워커 노드의 메모리 여유가 넉넉하지 않다면 Postgres를 3-replica로 올리기 전에 여유를 확인할 것.

10.4채널 추가

클러스터 에이전트는 데스크톱 Agents 화면에 나타나지 않는다 — 데스크톱이 프로세스를 spawn하지 않기 때문이며, 그것이 24시간 상주의 조건이다. 채널 참여는 CLI로 한다.

kubectl exec -n buzz deploy/buzz-agent-<name> -- buzz channels join --channel <UUID>

실행 중인 에이전트가 멤버십 알림으로 자동 구독한다. 재시작은 필요 없다.
